# DNS原因チェーンと画面状態による比較

ユーザー実機報告では、Chromeはauth.openai.comから別ホストへのリダイレクト応答を受信し、アプリはコード交換でDNS_LOOKUP_FAILED・HTTP未取得となった。Chrome経由の到達性は確認できるが、Chromeの既存接続・キャッシュ・セキュアDNS・プロキシと、アプリの標準名前解決経路が同じとは限らない。リダイレクト後の白画面は別の観測であり、認証元ホストのDNS障害の証拠とはしない。原因は未確定。

## ソースで確認したこと

| 項目 | 確認結果 |
| --- | --- |
| loopback | ServerSocketを127.0.0.1へbindする待受け設定だけ。外部HTTPSは別のHttpsURLConnectionで作る |
| プロセス／socketのネットワーク固定 | bindProcessToNetwork、setProcessDefaultNetwork、Network.bindSocket、Network.openConnectionの呼出しなし |
| アプリ独自のDNS・プロキシ設定 | なし。外部HTTPSはAndroid標準スタック。新しい比較用lookupも標準InetAddressで、実際の接続先を置き換えない |
| OS／VPN等の経路 | 端末のPrivate DNS・VPN・システムプロキシ・アプリ別制限の実状態は未確認。ソースに設定がないことだけでは除外できない |

DNS分類は例外メッセージの文字列検索ではなく、最大8段の原因チェーン内に実際のUnknownHostExceptionがあるかで判定する。単にメッセージへDNSやUnknownHostExceptionと書かれているIOExceptionはDNSと分類しない。

HTTPの例外を安全なProblemへ変換する前に、外側→原因のクラスを固定の許可リストへ対応付ける。java.net.UnknownHostException、java.io.IOException、javax.net.ssl.SSLHandshakeException、android.system.GaiException、android.system.ErrnoException等だけを固定名で表示し、未許可クラスはOTHER、打切りはTRUNCATEDとする。android.systemのクラスは名前の照合のみで、隠しAPIの呼出しやerrno・メッセージの読み取りはしない。

Exceptionのmessage、toString、stack traceは表示／保存しない。URL・query・認可コード・token・HTTP本文・IPアドレスも追加の診断へ渡さない。安全なクラス名・固定分類・既存の段階と固定ホストだけを、画面のメモリ内に保持する。接続先host表示はリクエスト宛先であり、プロキシ内部等で失敗した名前を推測したものではない。

## Androidだけでの比較

1. 最新APKで通常のContinue with ChatGPTを試し、失敗時の段階・固定分類・ホスト・例外クラスの順序を控える。通常ボタンでは追加lookupを実行しない。
2. 新しい認証として「診断用：DNS比較付きでサインイン」を押す。追加比較は認証情報を送らず、auth.openai.comの標準名前解決を行うだけ。解決したIPは保存・表示せず、外部接続にも使わない。
3. ブラウザで認証を終え、受信画面を確認してアプリへ戻る。次の3点を別々に確認する。各結果には画面表示中／非表示中／比較中に状態変化の区別が付く。

| 比較点 | 実行タイミング |
| --- | --- |
| 認証前 | ブラウザ起動前 |
| callback検査後 | callbackを検査して登録情報を保存した後、コード交換の前 |
| アプリ復帰時 | 認証開始後、画面が非表示→表示になった最初の時点。別画面への移動・回転等でも起こり得る |

復帰がcallbackより先なら復帰時の比較も先になるため、行の表示順を時刻順とは解釈しない。比較中に表示状態が変わった行を、非表示中だけの測定とは扱わない。

比較は1点につき待機上限5秒。DNS自体のOS処理は中断できない場合があるため、最大2本のlookupスレッドに限定し、待機を打ち切った結果や古い認証試行の結果は使わない。未実行の行は成功／失敗と推測せず、ユーザーがキャンセルした、callbackが来ていない、別操作へ進んだ等の可能性も確認する。全結果を確認してから次の操作を行う。

比較はDNSキャッシュを温め、最大数秒ずつコード交換を遅らせる可能性がある。そのため通常試行と比較試行は分ける。比較は原因調査専用で、サインインの修正策・事前名前解決の恒久的な回避策としては採用しない。認証ごとに新しいコードを発行し、古いcallbackは再利用しない。

## 結果の読み方

| 観測 | 次に調べる候補（断定ではない） |
| --- | --- |
| 認証前成功、非表示中callback後失敗、復帰時成功 | バックグラウンド通信制限、ネットワーク切替、タイミング等。画面状態が途中で変わった測定は区別する |
| 3点とも失敗、Chromeは応答受信 | 標準resolverとブラウザ独自resolver／キャッシュ、アプリ別VPN・制限、OS経路の差 |
| 3点とも成功、コード交換だけDNS失敗 | HTTPスタック・システムプロキシ等の経路差や測定時刻の差。どの名前が失敗したかは推測しない |
| 比較付きでのみ成功 | キャッシュ・タイミングに影響された可能性。原因解消や恒久修正とは扱わない |

比較lookupの例外にはFutureのExecutionExceptionが外側に付くことがある。HTTPの例外と比較する際は、その後ろの原因クラスも見る。OTHERを含む場合は任意のクラス名を追加で要求せず、表示済みの安全な分類だけを報告する。

[従来のネットワーク比較手順](android-dns-check.md)と合わせ、Wi-Fi／モバイルの種別、通常／比較付き、3点の固定結果、画面状態、コード交換の例外クラス順だけを記録する。URL・コード・token・本文・IPは不要。DNS設定・VPN・プロキシ設定の変更、固定IP接続、TLS検証の緩和は行わない。この診断版の実機試験は未実施で、原因や修正策はまだ確定していない。
