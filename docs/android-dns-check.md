# 認可コード交換のDNS失敗を切り分ける

2026-11-04。ユーザー実機報告では、認可コード交換でDNS失敗、HTTP未取得、トークン未保存、INTERNET権限ありだった。失敗段階は判明したが、原因は未確定。この修正後の実機再試験は未実施。

## 公式仕様と実装の照合

[現在の公式sign-in仕様](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)と照合したコード交換先は、schemeがHTTPS、ホストが `auth.openai.com`、pathが `/api/accounts/oauth/token`。実装は一致し、ソース上のホストに空白混入は見つからなかった。固定の `TOKEN_ENDPOINT` をコード交換・更新で共用する。認可コードはURLのqueryではなくform本文へ入れる。

接続前にURIを検査し、空白・制御文字・不可視文字による不正host、許可対象外host、userinfo、平文HTTP、固定IP宛て等は拒否する。黙って空白を削除する処理はない。拒否時は `INVALID_ENDPOINT` とホスト未確定を表示し、不正な文字列は反射しない。

名前解決は標準の `HttpsURLConnection` とAndroid側の処理に任せている。独自DNS、DoHクライアント、名前解決結果の独自キャッシュ、固定IP接続はない。既存の `InetAddress` 利用はcallback用 `127.0.0.1` listenerのbindで、コード交換先ではない。INTERNET宣言、HTTPS限定、標準TLS検証、redirect禁止を維持し、DNS・VPN・証明書の設定は変更していない。

## 追加した安全な表示

接続先を検査してから、許可済みの固定値 `auth.openai.com` または `api.openai.com` と対応付けて診断へ渡す。任意のURLから取り出した文字列を表示しない。固定エラー分類は `DNS_LOOKUP_FAILED`、`TLS_FAILED`、`TIMEOUT`、`CONNECTION_FAILED`、`IO_FAILED`、`PERMISSION_DENIED`、`HTTP_ERROR`、`INVALID_ENDPOINT` 等のアプリ内列挙型。例外本文やサーバーのコード文字列ではない。

URL全体・path・query・認可コード・token・生の例外メッセージは診断へ表示／記録しない。既存の診断と同様に列挙型と数値だけで構成し、ログ・ファイルへの追加保存もしない。

## Androidだけでの確認手順

最初に現在の診断を控える。次の操作で診断が更新されるため、各試験を分けて記録する。

1. 最新APKへ更新し、失敗時の「接続先ホスト」と「固定エラー分類」を確認する。`auth.openai.com` と `DNS_LOOKUP_FAILED` なら許可済みホストへの名前解決に失敗している。`INVALID_ENDPOINT` なら名前解決前の接続先検査で停止している。
2. 同じ端末・同じネットワークで、ブラウザから[認証情報を要しない公開OpenID確認先](https://auth.openai.com/.well-known/openid-configuration)を開く。認可URLやcallbackをコピーしない。「開けた／名前解決エラー／接続エラー」だけを記録し、本文JSONやアドレスバーは貼り付けない。404等でもHTTP応答を得られたなら、そのブラウザでは到達しており、DNS失敗とは別。
3. 利用可能ならインストール済みの別ブラウザでも同じ公開先を確認する。ブラウザのセキュアDNS・プロキシ・既存接続・キャッシュにより、ブラウザとアプリの結果が異なることがある。ブラウザ成功だけでAndroidの標準DNSやアプリ通信が正常とは断定しない。
4. AndroidのPrivate DNS、VPN・広告ブロック、データセーバー、アプリ別のモバイル／Wi-Fi通信許可・バックグラウンド通信制限、ブラウザのセキュアDNSについて、現在の有無・モードだけを確認する。設定は変更しない。接続先設定・アカウント・認証情報の共有は不要。
5. 利用可能ならWi-Fiとモバイルデータで、公開先とアプリの新しいサインインを比較する。これは検証のためのネットワーク比較であり、DNS設定の変更ではない。毎回Continue with ChatGPTから新しい認証を開始し、古いコードやcallbackを再利用しない。通信料にも注意する。

| 結果 | 判断できる範囲 |
| --- | --- |
| 複数ブラウザとアプリが同じネットワークで失敗し、別ネットワークでは成功 | そのネットワークのDNS・経路・制限等を疑う。URL誤りと即断しない |
| ブラウザ成功、アプリはauth.openai.comでDNS_LOOKUP_FAILED | 端末全体一律の障害とは断定できない。ブラウザ独自DNS／キャッシュ、アプリ別VPN・通信制限、アプリ／OSの標準通信経路の違いを調べる。これだけでコード不具合とも断定しない |
| アプリがINVALID_ENDPOINT | DNS前に接続先検査で拒否。固定分類と試験条件を報告し、実装・インストール済みAPKを確認する |
| HTTP状態を取得、またはTLS_FAILEDへ変化 | DNS段階から進んだ可能性があるが、サインイン成功ではない。新しい段階・固定分類・HTTP状態を記録する |

報告は、ネットワーク種別（SSID不要）、ブラウザで公開先を開けたか、アプリの段階・固定ホスト・固定分類・HTTP状態・保存状態に限定する。原因が確定するまでは、DNS変更、VPN／保護機能の無効化、固定IP接続を修正策として採用しない。
