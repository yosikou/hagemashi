# 保存済み回答だけを使う予約通知検証

UI整理PR #8のffe9ac2c18728d94c11c607c0442766509c27ed4から分岐し、モデル利用不可時の案内を補強した親先端f1ea23cfce3a5495222661e3ac4f5bd021731e83も取り込んだ。feat/saved-answer-reservationsのbaseをfeat/home-settingsにする。#5→#6→#7→#8→本PRの依存関係で、今回どれもマージしない。UI版だけのAPKと、この予約版APKを取り違えない。後続のため、親を取り込む場合は順にmainへbase変更・固有差分とCI確認が必要。

## 検証範囲

設定→通知で「最新の保存済み回答を検証対象にする」を明示的に選び、そのIDの保存済み回答だけを毎日通知する。別の回答を生成しても、対象は自動で最新へ切り替えない。通知本文は既存の安全判定済み短文のみで、タップはその回答の全文・生成当時の人格名・実際の使用値と期間へ進む。旧回答に人格名がなければ補わない。

予約の登録・実行・通知タップはChatGPT／Health Connectにアクセスしない。通常の手動生成も通知しない。既存の詳細画面の明示的な「通知を試す」は日次予約とは別の検証操作である。

## 予約の方式

新しいライブラリは追加しない。API26以上のAlarmManager.setAndAllowWhileIdleによる**正確な時刻を要求しない**一回アラームを、次の端末現地時刻に登録する。実行後に次の未処理日を登録する。正確なアラーム権限やForeground Serviceは使わない。Androidの省電力・Doze・端末メーカーの制限で遅れたり抑止されたりするため、時刻厳守や未試験端末での配信を保証しない。

通知オン／時刻／検証対象変更時に設定の予約世代を増やし、旧世代のPendingIntentとアラームをキャンセルする。残っていた配送要求も、最新のオン・世代・日付・時刻を受信時に検査して拒否する。オフは将来の予約を止め、既に表示された通知を勝手に消さない。設定保存と配送判定は同じプロセス内ロックを共有する。Androidが既に配送中の通知まで原子的に取り消せるという意味ではない。

起動・通知権限からの復帰時は予約を再照合する。再起動、端末時刻変更、タイムゾーン変更、アプリ更新でもローカルReceiverで再登録する。登録済みの当日分が遅延している場合は当日中に再登録できるが、前日分は翌日に通知しない。夏時間の存在しない時刻はJava Timeの現地時刻解決に従って後へずらし、重複時刻は先の時刻を使用する。同じ現地日付では再度処理しない。

追加権限はRECEIVE_BOOT_COMPLETEDのみ。既存のPOST_NOTIFICATIONSを明示操作で要求し、通知不可・未指定・回答読取不可は配信停止と表示する。設定済みと予約登録済みを区別する。権限許可後にアプリへ戻ると未来の予定を登録し、許可しただけでAI生成や即時の検証通知を送らない。

## 同日重複と失敗の扱い

日付の処理記録は別のKeystore alias／noBackupFilesDirへ暗号化保存し、再試行・時刻変更・オンオフ・プロセス再作成でも忘れない。通知を呼ぶ**前**に当日を永続記録する。これにより同日重複を防ぐ一方、記録とAndroid通知の間でプロセスが終了すると通知が欠ける可能性がある。ファイル保存とOS通知に共通トランザクションはないため「必ずちょうど一度」を保証せず、重複防止を優先する。当日処理済みの表示も配信成功の断言ではない。

処理記録は健康値・回答本文を含まず、日付・予約世代・固定の結果分類だけ。過去の日付の記録を勝手に消して時計の巻き戻しで再配信することはしない。台帳や鍵が壊れた場合はリセットして通知するのではなく、停止する。保存上限などの障害時も安全に停止する。診断ログに健康値・回答・送信内容・token・生の例外を出さない。

日次通知のtagは日付別で、前日の通知が残っていても当日のものを新しく出せる。PendingIntentの遷移先は回答IDなので、通知日や現在の最新回答へ差し替えない。

## 無操作AI生成は接続しない

SIWCの利用条件と、アプリ非表示中の通信が確認できるまでは、予約実行から生成クライアントを呼ばない。このReceiverはローカル保存と通知だけで、APIのbackground機能とも別のもの。

将来自動生成をつなぐ際は、予約作成時ではなく実行時に保存されたエージェント・人格・補足を読み、設定スナップショットをその生成で固定する。モデル利用不可時は選び直しを案内し自動代替しない。通信失敗の再試行は当日内だけ、前日分は翌日に通知しない。手動生成が実行中なら同時実行せず当日内の再試行へ回す必要がある。今回の予約通知はAIを呼ばないため、この通信・生成競合制御を実装済みとは扱わない。

## Androidだけでの試験

1. この予約PRの診断APKを既存のhagemashi診断へ上書きする。アンインストール・データ削除・署名キー再生成は不要。親UI PRのAPKには予約処理がないため、PRリンクとビルド識別子を確認する。
2. 既存の保存済み回答がホームにあればそのまま使える。なければ通常の手動生成で回答を用意する。この準備以外、予約の設定・配信・再配信確認ではAIに送らない。
3. 設定→通知で「最新の保存済み回答を検証対象にする」を押す。表示された対象IDを確認する。通知権限とAndroidのアプリ／チャンネルを許可してアプリに戻り、オンにして現地時刻で少し先を選ぶ。「予約登録済み」になっていることを確認する。
4. 配信前に時刻をさらに後へ変え、古い時刻では通知されないことを確認する。アプリを最近使ったアプリから閉じて待つ。正確な時刻指定ではないため余裕を持って待ち、実際の到着時刻を確認する。OSの強制停止はアラームを取り消すため、この通常終了試験とは分ける。
5. 通知に測定値が出ず、タップで対象の回答・人格名・使用値と期間を開けることを確認する。必要なら別の回答Bを生成しても、明示的に対象を変更しない限り予約はAを開くことを確認する。
6. 同じ日に時刻を変える・オフ→オン・アプリ再起動を行っても、日次予約の通知が重複しないことを確認する。当日処理済みなら翌未処理日を予定するため、同日の検証通知をもう一度強制発行する機能は設けていない。詳細画面の明示的な通知テストをこの重複件数に混ぜない。
7. 配信前のオフで予約が止まること、通知権限拒否時は設定済みでも配信停止と表示されること、通常手動生成で通知しないことを確認する。対象回答の全文は権限拒否でもアプリ内で読める。
8. 別日に翌日の通知を確認する。必要ならタイムゾーン変更・端末再起動による再登録を確認する。未実施の条件は未確認と報告する。端末設定を変えることを合格の前提にはしない。

報告はビルド識別子・予約時刻・実際の到着時刻・各成否だけでよい。健康値、回答、人格の私的内容、認証情報を貼る必要はない。

## 検証

JVMで現地日付、翌日、オンオフ・対象なし、旧世代、古い時刻、前日持ち越し拒否、再作成後の重複、夏時間、時計巻き戻し、破損台帳を合成値だけで検証する。CIは両variant単体テスト、Lint、アプリとUIテストAPKをビルドする。実機の予約到着・Doze・再起動・端末別制約とconnectedDebugAndroidTestは未実行。CI成功をこれらの実機成功とは扱わない。UI試験は親PRの[手順](home-settings.md)も含め、実機確認後にマージを判断する。

公式根拠：[繰り返し・不正確アラーム](https://developer.android.com/develop/background-work/services/alarms/schedule)、[BroadcastReceiver](https://developer.android.com/develop/background-work/background-tasks/broadcasts)、[通知権限](https://developer.android.com/develop/ui/views/notifications/notification-permission)。
