# 認証情報なしの通信診断と継続署名

## 現在の目的

ChromeとTermuxでは同一端末・回線でHTTPS応答を受信でき、既存hagemashiはコード交換でDNS_LOOKUP_FAILEDとなっている。認証後すぐ復帰しても同じ結果だった。原因は未確定で、DNS設定・VPN・プロキシ・TLS・接続方式は変更しない。

既存APKの3世代（67741f7、6f7244d、ce49d62）は署名検証・ZIP整合性・APK内INTERNET宣言が正常だったが、署名証明書が全て異なった。versionCodeは全て1。旧版の秘密鍵は現環境・リポジトリから復元できず、APKの公開証明書から秘密鍵は復元できない。既存アプリはアンインストールしない。

## 最初の一度だけ：Termuxで署名Secretを登録

個人のTermuxでPython、GitHub CLI、keytoolを用意する。例は `pkg install python gh openjdk-21`。実機の配布元ではopenjdk-17が見つからなかったため、鍵生成には提供されるJDK21等を使う。JDK21も見つからない場合は `pkg search openjdk` でkeytoolを含む提供版を確認する。端末側の鍵生成はJDK17でなくてもよい。CIビルドはJDK17を維持する。

`gh auth login` で自分のGitHubへ接続し、yosikou/hagemashiのActions Secretを書き込める権限を使う。トークンをコマンド引数・チャット・ログへ貼り付けない。

PRでレビューした `scripts/register-signing-secret.py` を端末内へ取得して、`python register-signing-secret.py` を実行する。実行するコードの取得元commitを確認する。このスクリプトは：

- 新しいRSA3072／PKCS12の診断署名鍵を端末内だけで生成する。既存版の署名鍵を復元したと扱わない。
- 鍵とランダムなパスワードを一つのActions Repository Secret `HAGEMASHI_SIGNING_BUNDLE` へ標準入力経由で登録する。
- 端末の `~/.local/share/hagemashi-signing/signing-bundle.json` に復旧用情報を権限600（親ディレクトリ700）で保存する。このファイルは秘密鍵を含む。共有ストレージ・Git・チャット・ログ・Artifactsへ移さない。端末やTermuxを消す前に、所有者が管理する安全な方法で保管する。
- 登録済みSecretがあれば上書きせず終了する。生成済みの端末内ファイルがあれば、新しい鍵を生成せず同じものを使用する。
- 成功時には公開証明書のSHA-256だけを表示する。報告するなら「登録完了」と公開fingerprintだけでよい。秘密ファイルやその内容は送らない。

CIはSecretを一時ディレクトリへ復元し、パスワード・鍵文字列をマスクしてからGradleへ渡す。公開ArtifactsはAPKと検証レポートに限定し、終了時に一時鍵を削除する。鍵をキャッシュ・Gitへ保存しない。Secret未設定時もチェックを実行するが、ランダム鍵のAPKは配布しない。フォークPRへSecretは渡らない。

Secret登録前に開始したCIには新しいSecretが反映されない場合がある。その場合は登録後に既存ジョブを再実行する。同じ実行の再試行ではArtifactsを新しいものへ置換する。Secretの削除・再生成は更新不能につながるため、通常のビルド時は変更しない。署名継続の確認は、異なる実行の証明書SHA-256を比較する。

## APKの取得と併存

Actionsが成功したら **hagemashi-diagnostic-apk** を取得・展開し `app-diagnostic.apk` を開く。通常版のhagemashi-debug-apkと区別する。

| 項目 | 既存版 | 新しい診断版 |
| --- | --- | --- |
| applicationId | com.yosikou.hagemashi | com.yosikou.hagemashi.diagnostic |
| アプリ名 | hagemashi | hagemashi 診断 |
| データ・Keystore | 既存領域を維持 | 別の新規領域 |

診断版から既存版の接続情報や履歴は読まない。新しい診断版の以後の更新は登録済み鍵で署名する。通常版も同じSecretで署名するが、旧来の別署名の通常版を上書きできるとは扱わない。versionCodeを増やすだけでは署名不一致は解消しない。

## まとめて行う実機試験

1. 既存版を残したまま「hagemashi 診断」が別アイコンで追加されたことを確認する。端末設定は変えない。
2. ビルド識別子を確認する。CIではcommit・run ID・attemptが組み合わされる。「通信診断（認証不要）」を開く。ここでサインインは不要。画面を開いただけでは外部通信しない。
3. 「DNS名前解決を実行」を押し、完了を待つ。
4. 「HTTPS GETを実行」を押し、完了を待つ。固定ホストのルートへGETし、リダイレクトは追わない。TermuxのHEADとはmethodが異なるため、ステータスの一致を必須にしない。
5. 「認証情報なしの空POSTを実行」を押し、完了を待つ。通常のコード交換先へ、Authorizationなし・空のform本文を送る。認可コード等は含めない。400等もHTTP応答受信という結果になる。
6. 「安全な診断結果をコピー」で3件をまとめてコピーする。クリップボードへ出すのはこの固定形式だけ。アカウント名・メール・URL・query・本文・IP・生の例外メッセージは含まれない。別途、回線種別とOSバージョンを添える。未実行の診断は行がなく、成功と推測しない。
7. 必要に応じて通常の手動サインインを試す。認証不要診断と通常認証は同じHttpの接続・TLS・timeout・redirect禁止・例外分類処理を使うが、空POSTは本物の認可コード交換成功を証明しない。
8. 後のCIで同じ診断版をインストールし、アンインストールせず更新できることを確認する。実際の更新成功は実機確認まで未検証。

1種類につき最新1件だけをメモリ内に保持する。再実行でその種類を置換し、プロセス終了で消える。コピー操作はOSのクリップボードへ保存する。処理段階の画面表示も確認できる。キャンセルした診断は結果行を作らず、画面にCANCELLEDを表示する。診断はViewModelのExecutorで処理し、通常のブラウザ表示で自動キャンセルしないが、OSによるプロセス停止への継続保証はない。

## 固定レポートの解釈

- `DNS_RESOLVED`：標準resolverで解決。IPは保存・利用しない。
- `HTTP_RESPONSE_RECEIVED` とHTTP番号：HTTPS応答が返った。400・403も含み、認証成功やSIWC適用承認ではない。
- `DNS_LOOKUP_FAILED`：最大8段の原因チェーン内にUnknownHostExceptionがある。DNS分類が他の分類より優先される。表示された安全な原因列も合わせて見る。
- `NOT_RECEIVED`：有効なHTTP状態を取得していない。成功状態を補完しない。
- `OTHER`／`TRUNCATED`：許可外の例外名／原因列の打切り。生のメッセージやクラス名の追加収集は求めない。
- `visibility`：診断全体の開始・終了時に表示中／非表示／変化したか。途中の一瞬の切替やOS制限を完全に記録するものではない。

3件とも成功し通常認証だけ失敗なら、コード交換時のタイミング・バックグラウンド状態等を比較する。DNSのみ成功しGET／POSTがDNS失敗なら、HTTPスタック／システムプロキシ等の経路差を候補とする。どちらも原因確定とは扱わない。事前lookupでキャッシュが温まる可能性があるため、通常認証との試行順も記録する。

この版の実機動作・インストール／更新・通信障害の原因解消はユーザー試験まで未確認。認証更新・利用上限・Androidへの正式適用等も未確認のまま。
